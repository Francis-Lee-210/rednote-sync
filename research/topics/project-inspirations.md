## 001. 用后台浏览器加载帖子详情，直接保存响应数据

来源：对 [`xhs_web_crawler` 采集流程](../projects/xhs-web-crawler/review.md#先读这里身份验证与帖子详情获取)的讨论，以及 [Playwright 通用浏览器能力研究](../projects/playwright/review.md)。

**可以让脚本在后台运行一个浏览器，逐条打开帖子并读取详情；不必一直显示浏览器窗口，也可以省掉手动导出 HAR 的步骤。** 这是根据工具能力提出的候选方案，尚未在当前小红书页面上验证。

### 后台运行可以分成三种方式

| 方式 | 是否需要浏览器 | 怎样获取数据 |
|---|---|---|
| `xhs_web_crawler` 现有扩展 | 需要保留浏览器和目标页面 | 扩展自动点击，再由用户手动导出 HAR，交给 Python 解析 |
| Playwright 后台脚本 | 需要浏览器进程，但可以没有窗口 | 脚本控制页面，逐条打开帖子并读取网页收到的响应 |
| 纯 HTTP 脚本 | 不需要浏览器 | 直接请求接口，自行满足接口的认证、参数等要求 |

第一行是参考项目固定版本中的流程，详见[专项审查](../projects/xhs-web-crawler/review.md)。后两行是可以评估的实现方式；直接 HTTP 请求无需加载页面的通用机制见 [API testing](https://playwright.dev/python/docs/api-testing)。这些工具能力不代表小红书的对应访问链路已经可用。

Playwright 支持 **headless（无头）模式**：浏览器不显示窗口，但浏览器进程仍在后台加载网页、执行 JavaScript、操作页面。Python 或 Node.js 脚本可以自行启动独立的浏览器，无需提前打开日常使用的 Chrome。[浏览器模式说明](https://playwright.dev/python/docs/browsers#chromium-headless-shell)

### 可以省掉 HAR 这个中间步骤

`xhs_web_crawler` 的流程把网络响应先存进 HAR，再由 Python 从文件里提取笔记。自己实现时，可以由 Playwright 监听打开帖子所产生的目标响应，直接读取响应 JSON，再保存需要的笔记字段。[网络监听](https://playwright.dev/python/docs/network#network-events)、[响应 JSON 读取](https://playwright.dev/python/docs/api/class-response#response-json)

可以设计成下面的流程：

```text
指定页面或帖子清单
        ↓
后台浏览器逐条打开
        ↓
等待详情响应并读取数据
        ↓
核对帖子 ID 和需要的字段
        ↓
保存 JSON，记录成功和失败
```

任务范围可以由指定页面决定，也可以由一份帖子清单决定。采用清单方式时，仍要先确认每条帖子有可用的访问入口，以及所选采集账号能够访问它。

这条流程讨论的是详情 JSON 的获取与保存。图片、视频地址可以作为详情字段保存；媒体文件下载和校验需要另外实现。若某种打开方式没有产生预期的详情 JSON 响应，应记录为待分析结果，进一步确认该页面实际怎样加载数据。

### 候选验证顺序

如果要保留“让网页正常加载详情”的方式，可以优先评估 **Playwright + 独立浏览器会话 + 直接保存响应数据**：

1. **先用可见窗口验证单帖**：确认采集账号的登录状态，打开一个目标帖子，检查能否取得对应的详情数据。
2. **验证直接保存**：读取目标响应，核对帖子 ID、正文等所需字段，保存 JSON；失败或缺字段时留下明确记录。
3. **再验证无头模式**：使用同一小批目标，比较可见窗口与无头模式的访问结果、字段和失败情况，再判断是否适合后台运行。

以上只是建议的验证顺序，本条启发尚未实施。仍需确认登录状态如何建立和续期、不同页面的实际响应来源，以及无头模式下的稳定性；出现登录失效或需要人工验证时，应暂停并交回用户处理。浏览器模式本身不能证明账号安全或采集可靠。

更深入的能力与失败边界见[Playwright 浏览器路线专题](playwright-human-like-route.md)。该专题保留其历史研究范围；本条记录不改变现有实验状态或产品决策。

## 002. 用 Azure 临时虚拟机为本机脚本提供 HTTP 代理

记录日期：2026-09-13。来源：对 [RedCrack 代理配置与会话实现](../projects/redcrack/review.md)的讨论，以及下列 Azure、Tinyproxy 和 OpenSSH 官方资料。

**可以临时租一台 Azure Linux 虚拟机，让它充当 Mac 上脚本的网络中转站。** 候选组合是 **Azure Linux 虚拟机 + HTTP 代理 + SSH 隧道**：脚本继续在 Mac 运行，代理程序部署在云端，SSH 提供两者之间的加密连接。Azure 支持通过 SSH 连接 Linux 虚拟机；Tinyproxy 提供 HTTP/HTTPS 代理，OpenSSH 支持将本机端口转发到远端。[Azure SSH 文档](https://learn.microsoft.com/en-us/azure/virtual-machines/linux-vm-connect)、[Tinyproxy 官方说明](https://tinyproxy.github.io/)、[SSH 本地端口转发](https://man.openbsd.org/ssh#L)

本条仅记录配置思路与示意，尚未创建 Azure 资源、安装代理、建立隧道或运行 RedCrack；是否采用仍待确认。

### 通俗理解与连接路径

```text
Mac 上的脚本
    ↓ 使用 http://127.0.0.1:7890
Mac 本地代理入口
    ↓ SSH 加密隧道
Azure 虚拟机上的 HTTP 代理
    ↓ 经 Azure 网络出口
目标网站
```

这里的 `127.0.0.1:7890` 是 Mac 上的隧道入口，实际代理程序在 Azure 虚拟机里。代理决定请求经由哪里发出；`web_session` 等会话凭据用于表达登录状态，两者职责不同。

RedCrack README 的示例写了“配置代理（必须）”，但固定版本代码的 `proxy` 默认是 `None`，也有未配置代理时继续创建连接的分支。作者没有说明“必须”的原因，因此不能把代理视为该程序强制要求的参数；实际连接结果仍需验证。[README 示例](https://github.com/Cialle/RedCrack/blob/a557e328b6e723f63dcd75f1c52640794f2c84b5/README.md#L83-L91)、[可选参数](https://github.com/Cialle/RedCrack/blob/a557e328b6e723f63dcd75f1c52640794f2c84b5/request/web/xhs_session.py#L416-L425)、[无代理分支](https://github.com/Cialle/RedCrack/blob/a557e328b6e723f63dcd75f1c52640794f2c84b5/request/web/xhs_session.py#L106-L119)

### 配置步骤与最小示意

1. **创建专用临时资源组和 Linux 虚拟机。** 先确定订阅、地区、规格和预计使用时长，再核算费用。为虚拟机配置公网 IP，并检查出站连通性；Azure 公网 IP 可用于虚拟机的入站连接和可预测的出站地址。[公网 IP 说明](https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/virtual-network-public-ip-address)
2. **设置 SSH 连接。** 使用 SSH 密钥登录，把 SSH 入站来源限定为自己的公网 IP；代理服务只监听虚拟机本地地址，代理端口通过隧道供本机使用。
3. **在虚拟机上安装并配置 HTTP 代理。** 以下是 Tinyproxy 的最小配置示意，实际安装版本与启动方式需要在部署时确认。`Listen` 和 `Allow` 将入口限定在虚拟机本机；`ConnectPort 443` 允许通过 CONNECT 转发常见 HTTPS 连接。[Tinyproxy 配置说明](https://tinyproxy.github.io/#quickstart)

```conf
Port 8888
Listen 127.0.0.1
Allow 127.0.0.1
Timeout 600
ConnectPort 443
```

4. **在 Mac 上建立 SSH 隧道。** 将下面的密钥路径、用户名和公网 IP 占位符替换为实际部署值。命令把 Mac 的 `7890` 端口连接到虚拟机本机的 `8888` 端口；保持 SSH 连接期间，本机程序可以使用该入口。[OpenSSH 参数说明](https://man.openbsd.org/ssh#L)

```sh
ssh -i /path/to/azure-key.pem -N \
  -L 127.0.0.1:7890:127.0.0.1:8888 \
  azureuser@VM_PUBLIC_IP
```

脚本中的代理地址可填写为：

```python
proxy = "http://127.0.0.1:7890"
```

`7890` 和 `8888` 都是示例端口。部署时选择空闲端口，并同步修改隧道与脚本配置。上述代理入口需要云端代理和 SSH 隧道同时运行，单独填写地址不会建立连接。

### 临时使用、费用与清理

先以不含账号资料的普通 HTTPS 请求检查代理连通性，再核对实际出口是否符合部署预期。SSH 登录成功本身不能证明代理配置正确，也不能证明目标网站接口可用。

用完后断开 SSH 隧道，并删除只包含本次临时资源的专用资源组，核对虚拟机、磁盘和公网 IP 等资源已删除。资源组删除会处理组内资源；创建时就把临时资源与其他项目分开，方便完整清理。[Azure 资源组删除说明](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/delete-resource-group)

仅关闭虚拟机操作系统可能仍产生计算费用；释放计算资源后，磁盘和部分网络资源仍可能计费。“临时使用”需要落实资源清理，不能只依赖关机。具体费用按实际区域、规格、资源和使用时长核算，本条不预设免费额度或价格。[虚拟机状态与计费](https://learn.microsoft.com/en-us/azure/virtual-machines/states-billing)

### 待验证问题与记录边界

- Azure 订阅的可用地区、虚拟机规格、配额、预算与实际使用时长。
- HTTP/HTTPS 代理是否连通，网络出口是否符合预期，隧道断开后客户端如何报告失败。
- RedCrack 或其他客户端接入代理后的实际行为；配置了代理不等于登录、请求签名或帖子详情获取已经成功。
- Azure 提供云端网络出口，尚无本项目实测证据表明它可以解决小红书接口错误。代理连通与平台访问结果分别验收；现有实验状态与恢复条件仍见[协议实测说明](../reverse/targets/xhs-xsec-token/experiment/protocol-method.md)。

官方资料于 2026-09-13 核对；RedCrack 依据固定 revision `a557e328b6e723f63dcd75f1c52640794f2c84b5`。上述组合、端口配置和验证顺序是候选方案，没有部署或平台实测结果。

## 003. 提供帖子清单和 Cookie，在后台导出并记录逐帖进度

记录日期：2026-09-13。来源：用户提出的后台导出目标，以及补充作为技术路线参考的 [xhs 客户端](../projects/xhs/review.md#先读这里身份验证与帖子详情获取)、[RedCrack 的 HTTP 请求流程](../projects/redcrack/review.md#先读这里身份验证与帖子详情获取)和 [MediaCrawler 的采集流程](../projects/mediacrawler/review.md#先读这里身份验证与帖子详情获取)。本条先记录用户目标，再整理候选流程；不代表这条在线链路已经实现。

### 用户希望得到的使用体验

**用户已经拿到需要导出的帖子列表后，只需提供所选采集账号的 `web_session` 或自己的 Cookie，就能启动后台导出。程序自动处理整份清单，持续记录哪些帖子导出成功、哪些失败、哪些还需要进一步处理；中断后可以接着完成剩余部分。**

用户希望实际导出时不需要打开和操作浏览器。结合 RedCrack 带来的启发，优先评估直接由程序发 HTTP 请求、无需浏览器进程的方式；第 001 条的无头浏览器仍需要浏览器进程，是另一种候选实现。

这里的导出包括目标帖子的正文、必要元数据和本次要求的图片／视频等媒体，并生成可在本地使用的文件。目标是自动完成整份清单；暂时无法完成的帖子也必须有明确记录，不能静默遗漏或计为成功。

### 预期流程

```text
已有的待导出帖子清单
        ↓
保存本轮清单，建立逐帖任务和初始进度记录
        ↓
选择采集账号，提供 web_session 或 Cookie
        ↓
检查会话是否有效、实际登录账号是否符合选择
        ↓
逐帖确认可用访问入口，缺少访问参数时尝试搜索定位
        ↓
HTTP 获取详情 → 下载所需媒体 → 保存并生成本地导出
        ↓
逐帖更新：导出成功／导出失败／待进一步处理
        ↓
恢复或补全时，继续处理未完成项并保留已有成果
```

清单决定本轮要处理哪些帖子。搜索在这里用于定位清单中的目标和取得配套访问参数，不自动把其他搜索结果加入导出范围；匹配时核对帖子 ID，不能只凭相似标题认定是同一篇。

如果清单已有适用于当前采集账号的有效访问入口，可以直接请求详情；缺少或无法使用时，再研究通过搜索等入口取得配套的 `note_id`、`xsec_token` 和 `xsec_source`。用户希望这些细节由程序处理，减少手动复制参数；能否在所选账号下自动取得，仍需逐项验证。

### 导出进度文档应该让用户看到什么

进入导出流程就建立进度记录，并在每帖结果或关键步骤变化后及时保存。可以自动生成类似 `导出进度.md` 的可读文档，具体文件名和格式尚未选定。运行中还应显示“待处理”和“处理中”，避免把尚未尝试的帖子当成失败。

| 用户关心的结果 | 含义 | 记录示例 |
|---|---|---|
| 导出成功 | 本次要求的详情和媒体已保存，必要校验通过，本地导出文件已生成 | 已保存正文与全部所需图片，并附本地输出位置 |
| 导出失败 | 已尝试处理，但某个具体步骤失败；保留已经完成的部分 | 正文已保存，3 张图片成功 2 张；记录剩余图片下载失败及重试建议 |
| 待进一步处理 | 当前方式不足以完成，需要检查访问入口、账号或后续处理方法 | 小号搜索没有找到目标帖子，等待检查是否需要主号补全 |

上述例子仅说明期望的展示方式，不是真实导出结果，也不新增或改写 Core 的状态枚举。“收到详情响应”“保存了图片地址”或“循环执行结束”都不足以单独标记整帖导出成功；如果只是本地导出文件生成失败，应记录为导出环节失败，优先利用已保存内容重新生成。

每帖至少应能查看：

- **是哪一篇、属于哪一轮：** 帖子 ID、标题、本轮任务，以及原始点赞／收藏清单归属。
- **谁处理过、处理到哪里：** 此次采集账号、当前步骤、结果、尝试时间与次数；正文、媒体和本地导出的分项完成情况。
- **为什么没完成、接下来怎么办：** 失败或待处理原因、尚缺的内容、建议的下一步，以及已有文件的位置。

总览应显示本轮总数、成功数、失败数、待进一步处理数、待处理数和正在处理数，并标明最近更新时间；每篇帖子在总览中只计入一个当前分类，具体缺口另列。登录会话、原始 Cookie、访问 token 和包含这些值的完整请求信息不写入进度文档，用账号标签或稳定身份引用记录采集来源。

### 小号搜索未命中时怎样保留后续工作

小号搜索未命中，只能说明“这次使用该账号、该搜索方式没有找到目标”。应将帖子保留在待进一步处理清单，记录未命中的环节和已尝试的方法；这不证明帖子已经删除，也不代表主号一定可以取得它。

用户检查后，可以将确实需要主号补全的未完成项转交主号，保留小号此前的结果和主号后续的结果。原始点赞／收藏关系始终归属原清单账号，不因采集账号改变而改归属；这与已有的[首轮采集与主号补全目标](../../docs/design/product-design.md#首轮采集与主号补全)一致。

普通单帖失败应记录后继续其他帖子；登录失效、验证挑战或限流则属于会话／运行层面的中断，需要保存暂停原因和剩余任务。不要把这些情况一律写成“搜索未命中”，也不因它们自动切换账号继续。恢复时根据已保存状态，只补本轮尚未完成的部分；成功内容和历次尝试记录继续保留。

### 未验证技术路线：请求小红书详情接口

三个项目都提供由程序请求详情接口的实现参考，可以归纳为下面的流程。各项目怎样准备会话和签名、是否依赖浏览器，需要分别看待。

```text
准备会话 Cookie、帖子 ID 和访问参数
        ↓
为本次请求准备签名
        ↓
Python 发送 HTTP 请求
        ↓
检查并解析响应，提取帖子详情
        ↓
保存或导出
```

其中，**Cookie 表示使用哪个账号的会话，帖子 ID 和 `xsec_token` 等参数指定访问哪篇帖子，请求签名则是为本次请求准备的校验信息。** 三者用途不同，提供 Cookie 不会自动补齐目标帖子的访问参数。最后的“保存或导出”是本项目需要串起的后续工作，仍包括媒体保存、逐帖进度和失败恢复。

### 最少输入目标与三个参考项目的实际边界

用户希望的最少输入是 **“待导出清单 + 有效会话凭据”**。`web_session` 是 Cookie 中的一项，整组 Cookie 可能还包含其他请求需要的信息；能否只靠单项 `web_session` 建立可用会话，需要验证。程序还需要完成账号检查、请求构造、访问参数取得、媒体保存和失败恢复，才能把这些操作封装成简单的用户流程。

| 参考项目 | 身份验证方式 | 帖子详情获取方式 | 与本条目标的差距 |
|---|---|---|---|
| [xhs（ReaJason/xhs）](../projects/xhs/review.md) | 调用方提供 Cookie，交给 Python HTTP 会话；登录有效性和实际账号需要另行检查 | 提供帖子 ID 和访问参数 → 调用外部签名函数 → Python 请求详情接口 → 提取 `note_card` | 可以参考 Cookie 客户端和详情解析。作者的签名服务示例依赖浏览器，因此完整接口路线不能直接视为无需浏览器；完整批量导出、逐帖进度和可靠恢复还需补齐。 |
| [RedCrack](../projects/redcrack/review.md) | 调用方提供 `web_session`，程序初始化其他会话材料并放入该值；不提供时尝试建立游客会话 | 提供帖子 ID 和 token → Python 组织签名与请求 → HTTP 请求详情接口 → 调用方解析原始响应 | HTTP 路线无需浏览器，可参考会话与请求封装；没有串起完整批量导出、媒体保存和断点恢复。虽然有关键词搜索接口，固定版本的实现仍有已知错误。 |
| [MediaCrawler](../projects/mediacrawler/review.md) | 浏览器建立或恢复登录状态，再把 Cookie 交给 Python；外部 Cookie 分支先注入 `web_session` 再回读会话 | 从搜索结果或指定链接取得帖子 ID 和访问参数 → Python 调用 `xhshow` 准备签名 → HTTP 获取详情 → 存储，并按配置下载媒体 | 可以参考任务安排和采集／存储分层。启动／登录仍依赖浏览器；媒体下载默认关闭，已审查的开源版没有可靠断点续跑，不能直接视为“只提供 Cookie 就完成纯 HTTP 全量导出”。 |

上表聚焦详情接口路线。xhs 还提供直接下载帖子 HTML、解析内嵌初始数据的方法，由调用方自行选择；MediaCrawler 则在接口返回为空或重试耗尽等特定条件下尝试 HTTP HTML 备用路径。这些也可作为详情解析的参考，实际可用性仍需验证，不能据此推定任意接口失败都能自动补全。

这三个项目提供了不同部分的启发，完整使用体验需要结合现有 Core 实现。代理只是可选网络配置，第 002 条 Azure 方案不作为此流程的必备条件。

### 与现有 Core 的衔接和待验证事项

当前 Core 已有逐帖任务、失败与部分媒体状态、采集身份和尝试历史、恢复及本地导出能力，但当前发行包仍只支持离线输入。候选实现可以让在线采集器把规范化结果交给 Core，再从同一份已保存状态生成用户可读的进度文档；无需另建一套互不一致的进度事实来源。[身份与任务](../../projects/docs/sync-core.md#2-身份和任务)、[失败与恢复](../../projects/docs/sync-core.md#3-列表进度与失败隔离)、[保存与导出](../../projects/docs/sync-core.md#6-事实源提交与导出)

Core 现有索引和日志在导出阶段汇总，不能据此声称已经有本条所需的实时进度文档。在线采集器、搜索未命中的展示与转交操作、进度文档的持续刷新和状态映射仍需设计并验证。

后续验证围绕这个使用目标展开：

1. 提供有效会话后，能否在不启动浏览器进程的情况下确认所选账号，并取得清单中的单帖详情与所需媒体。
2. 清单缺少适用访问参数时，能否通过搜索精确定位目标；未命中和会话失效能否明确区分。
3. 能否分别记录完整成功、部分媒体失败、搜索未命中和本地导出失败，并让进度文档与已保存成果一致。
4. 中断、重启或主号补全后，能否继续未完成项，保留原清单归属、成功内容与各次采集来源。

先验证这些小范围情况，再扩大到整份清单；实际在线实验状态及恢复条件见[协议实测说明](../reverse/targets/xhs-xsec-token/experiment/protocol-method.md)。本次只整理想法，没有读取 Cookie、启动采集、修改 Core 或改变现有实验状态。参考版本为 xhs `f4b62d9f8e4078e631fc6e4ec8e430bc711ee9f0`、RedCrack `a557e328b6e723f63dcd75f1c52640794f2c84b5`、MediaCrawler `5665a271ef15e0ec82b1f48a951b66760e054db9`。
