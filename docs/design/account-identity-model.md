# 账号身份概念模型

状态：**概念草案**
更新日期：2026-09-12

本文为产品阶段二和阶段三建立共同语言；剩余未来能力仍属概念草案。2026-09-12 获准修复的 Core 身份拆分已实现，字段和行为以 [Core 实现契约](../../projects/docs/sync-core.md#2-身份和任务)及其输入文档为准；本文不重复定义协议。

## 为什么需要区分身份

Core 最初在历史实施 Stage 3 中采用单账号简化假设。产品允许列表关系、内容采集和未来写回由不同账号完成；本轮已将本地归档与列表、内容采集身份分开，真实在线账号链路仍需验收。

## 概念角色

| 角色 | 表达的问题 | 当前是否已建模 |
|---|---|---|
| 关系所属账号 | 点赞、收藏或收藏夹关系属于谁 | 已实现：归档 owner |
| 列表采集账号 | 哪个登录身份观察并导出了列表 | 已实现：可选列表来源身份 |
| 内容采集账号 | 哪个登录身份获取详情和媒体 | 已实现：可选内容来源与尝试历史 |
| 写回账号 | 未来由哪个身份执行点赞、收藏或收藏夹操作 | 尚未实现 |

这些角色可以由同一个账号承担，也可能不同。产品已确认用户可选择内容采集账号，并支持[首轮采集与主号补全](product-design.md#首轮采集与主号补全)；本草案不规定具体账号字段或运行协议。

## 概念状态

列表关系的发现和内容详情的获取是两类事实。一个帖子可以已经出现在点赞或收藏列表中，但尚未取得详情、媒体，或详情采集失败。当前 Core 已分别保存列表检查点与逐帖任务，内容失败不再阻止列表检查点前进；真实列表接入与访问范围仍需验证。

内容采集账号描述的是一次获取行为的执行身份，不一定是帖子整个导出过程中的唯一账号。例如，小号首轮搜索未命中，之后主号取得详情和媒体：点赞/收藏关系的所属账号没有变化，两次尝试却有不同的执行身份和结果。转交的是未完成工作，不是关系归属，也不能用主号的后续结果覆盖小号此前的失败事实。

单次尝试结果与帖子最终完成情况需要分别表达。已取得正文但缺少图片、搜索未命中后等待主号补全、主号补全后仍有缺口，都是需要保留的不同情况；移交完成不代表内容导出完成。本地任务状态、合并和恢复已在 Core 契约定义；真实账号转交的操作界面、在线授权和访问策略尚未实现。

## 与当前实现的关系

- `offline-input-v1` 仍是现行输入契约。
- `account`、scope 和 Note 标识仍指关系所属账号；来源身份是兼容旧 v1 的可选扩展，旧记录未提供的身份保持未知。
- 本地已覆盖小号失败、主号重试、保留成功媒体和尝试历史的合成回归；不能据此推定真实平台访问成功。

## 明确不决定

- 不决定字段名、枚举值、JSON 结构或 schema 版本。
- 不决定 Note、关系或媒体记录的主键。
- 不决定旧数据库和输入文件怎样迁移。
- 不决定三条账号路线的风险等级或账号组合限制。
- 不决定写回操作的授权、执行和验证协议。
