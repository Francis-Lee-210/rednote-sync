# 账号身份概念模型

状态：**概念草案**
更新日期：2026-08-18

本文只为未来产品阶段二和阶段三建立共同语言。它不是 `offline-input-v2`，不修改当前 Core，也不规定字段、主键、接口或迁移方式。

## 为什么需要区分身份

现有 Core 来自插件逆向得到的单账号工作流，并在历史实施 Stage 3 中继续采用了单账号简化假设。新产品构想允许列表关系、内容采集和未来写回由不同账号完成，因此不能继续把所有“账号”默认视为同一角色。

## 概念角色

| 角色 | 表达的问题 | 当前是否已建模 |
|---|---|---|
| 关系所属账号 | 点赞、收藏或收藏夹关系属于谁 | 当前与其他账号角色合并 |
| 列表采集账号 | 哪个登录身份观察并导出了列表 | 当前与顶层 `account` 合并 |
| 内容采集账号 | 哪个登录身份获取详情和媒体 | 当前与列表采集账号合并 |
| 写回账号 | 未来由哪个身份执行点赞、收藏或收藏夹操作 | 尚未实现 |

这些角色可以由同一个账号承担，也可能不同；当前草案不规定它们必须相同或必须分离。

## 概念状态

列表关系的发现和内容详情的获取是两类事实。一个帖子可以已经出现在点赞或收藏列表中，但尚未取得详情、媒体，或详情采集失败。未来协议需要能够表达这种分离，而不是要求每个列表项立即拥有成功或失败的详情结果。

## 与当前实现的关系

- `offline-input-v1` 仍是现行输入契约。
- 当前 `account`、scope、Note 标识和 Session 行为保持不变。
- 本文只记录未来接入三条账号路线时需要重新审视的概念边界。

## 明确不决定

- 不决定字段名、枚举值、JSON 结构或 schema 版本。
- 不决定 Note、关系或媒体记录的主键。
- 不决定旧数据库和输入文件怎样迁移。
- 不决定三条账号路线的风险等级或账号组合限制。
- 不决定写回操作的授权、执行和验证协议。
