## 当前优先级

当前最需要降低的是产品阶段二的不确定性。该阶段首先要解决不同内容采集账号如何处理阶段一确定的同一批帖子，再打通采集结果进入现有 Core 并可靠导出到本地的完整链路。阶段一可以在成熟个人脚本基础上继续工程化；阶段三的本地整理不需要在内容采集方案明确前提前定型。

2026-09-12 用户批准修复 Core 的六类问题：合法内容误拒、单帖失败阻塞、错误更新语义、全量存储/导出开销、单账号身份模型和自制构建门禁。实现边界见 [Core 当前契约](../../projects/docs/sync-core.md)；原架构审查保留为[分项实施记录与剩余候选方案](../history/2026-09-12-architecture-review.md)。本轮只使用临时合成库，没有真实数据迁移或新增平台请求。

2026-09-09 用户确认采集账号由用户选择，归档保留主号的点赞/收藏归属，登录方式优先支持 Cookie，见[产品设计](product-design.md#产品阶段二帖子内容下载与导出)。协议路线的最新已记录结果分为两项：

- [2026-09-12 G 对照](../../research/reverse/targets/xhs-xsec-token/experiment/protocol-method.md#2026-09-12-g-自有脚本身份及搜索成功)：未修改请求或签名代码，身份与搜索均 HTTP 200 / API 0，精确取得目标 token，结果为 `PROTOCOL_SEARCH_VERIFIED`。source 由搜索上下文设置；未请求详情、下载媒体或接入 Core。F 先前的搜索 461 仍是失败证据，不能据此把协议搜索概括为普遍不可用，也不能由 G 的成功断定旧账号失败原因。
- [2026-09-13 A–F 复核](../../research/reverse/targets/xhs-xsec-token/experiment/protocol-method.md#2026-09-13-af-身份复核与条件清理)：六个账号身份均 HTTP 200 / API -100，按当次授权清空 Cookie；G 保留原值并标为“小号”，本轮未请求 G。其当前有效性、续期和详情能力仍未验证。

这些是日期化实验结果，不代表当前会话仍有效。完整历史见[实验时间线](../../research/reverse/targets/xhs-xsec-token/timeline.md)。

### 已确认的推进顺序

1. 检查参考项目的 Cookie 登录逻辑，区分直接 HTTP 携带 Cookie、浏览器会话恢复与交互登录后保存 Cookie，明确成功判据。固定源码对照已完成，见[登录研究](../../research/topics/cookie-login-implementations.md)。
2. 先解决并验证用户所选采集账号的登录身份；G 的历史单次身份/搜索成功不能替代后续执行时的身份验证，续期与长期稳定性仍需各自验收。
3. 登录通过后，先获取主号清单中的一篇帖子及媒体，保留主号关系归属，并接入 Core 验证本地保存、重复执行和失败恢复。现有协议实验已取得一次目标搜索 token，详情仍未验收；媒体与 Core 不在该实验的完成判据中。
4. 单帖链路通过后，验证一次[首轮采集与主号补全](product-design.md#首轮采集与主号补全)：小号或其他账号未完成的帖子，经检查后转交主号低风险导出；合并成果时保留主号归属、各次采集来源和剩余缺口。
5. 单帖与跨账号补全链路均通过后，再扩大样本和数量，逐步验收全量完整性。

2026-09-09 用户确认了上述主号补全流程；本地身份表达、任务补缺和来源记录已在 Core 实现，真实账号采集及转交链路尚未验收。商家推广帖搜索未命中的历史观察是补全场景之一，不代表主号一定能取得这些帖子，也不能替代逐帖验收。

登录源码专项对照见[研究报告](../../research/topics/cookie-login-implementations.md)。其中的静态实现和比较变量不能代替用户所选账号的真实登录验证。

`xsec_token` 实验保留 F 搜索 461 和 G 搜索成功两类证据；G 的运行按仅搜索范围正常结束。后续执行范围和恢复条件以[实测说明](../../research/reverse/targets/xhs-xsec-token/experiment/protocol-method.md)为准，身份或搜索通过不自动授权详情、重试或换号。2026-09-14 本轮复核只同步既有证据并修复离线问题，没有新增平台请求。

2026-09-14 复核并修复了 9 月 9 日记录的两项脚本缺陷，离线回归通过；全量列表完整性、账号归属验证和中断恢复仍未完成工程验收。详情见下表和[本轮复核记录](../history/2026-09-12-architecture-review.md#11-2026-09-14-dsh-对话复核)。

历史实施阶段中的“离线输入桥接 → 扩展壳层 → 本地体验 → AI → 在线采集”只是当时逆向研究后的实施建议，不再代表当前产品优先级。

## 待研究问题

### 阶段一

- 点赞和收藏列表如何统一成稳定、可版本化的本地输出？
- 2000 多条扫描如何判断真正完成，并支持重复执行与中断恢复？

### 阶段二

- Core 已能表达 owner、列表采集与内容采集来源；真实在线适配器如何提供可靠的来源、采集时间和任务结果？
- Cookie 能否持续用于用户所选采集账号？G 在 2026-09-12 身份/搜索通过，A–F 在次日身份复核失效；G 未复测。续期、长期稳定性、目标帖子访问及不同列表上下文中的 token/source 发现仍是独立问题。
- 主号列表如何完整取得并保留关系来源？不能因其他账号成功登录就认定它能够读取主号的点赞/收藏列表。
- 三条账号路线分别能获取哪些字段和媒体？
- 如何用真实样本验证 Core 已实现的身份表达和每次尝试来源，确保输入声明与实际采集账号一致？
- 如何区分搜索未命中、账号访问范围、登录/限流、暂时网络问题、媒体缺失和本地保存失败，确定哪些未成功项需要主号补全，避免把本地错误变成主号重复访问？
- 主号低风险补全应使用哪些访问入口，如何限制频率和并发，遇到登录异常、安全挑战或限流时如何暂停和恢复？不能把这类账号或会话问题直接归为普通搜索未命中并立即切换账号继续。
- 本地尝试历史和只补缺已实现；真实账号转交如何操作，才能避免重复访问并验证最终缺口？
- 用商家推广帖等实际未命中样本，如何验证“首轮未完成 → 主号补全成功”与“主号仍无法取得”的两种结果，并分别记录详情、媒体和本地保存状态？
- 取得的详情和媒体应如何进入现有 Core，同时保留来源、失败和恢复状态？
- 主账号环境隔离的实际边界是什么？
- 低风险模式和高风险模式分别包含哪些请求或自动化行为？
- 风险、效率、成本和失败恢复应如何通过实验记录，而不是凭假设排序？

### 阶段三

2026-09-12 用户明确计划使用现有导出帖子探索知识库／LLM Wiki 构建方案。已准备独立来源快照和导入检查，下一步探索方法见 [LLM Wiki 候选试验](../explorations/llm-wiki.md#接入当前下载后的第一轮试验)；尚未确定具体整理方案、模型或界面。

同日新增明确需求：[按含义搜索帖子](product-design.md#按含义搜索帖子)，找回未出现查询词或近义词、但实际意义相关的帖子。此项能力尚未实现或验收。

2026-09-13 继续研究语义检索与 RAG／LLM Wiki 的组合方式，技术依据、候选实现和召回评估见[语义资料库研究](../../research/topics/semantic-post-library.md)。研究不代表已完成索引、模型选型或全库找回验收。

2026-09-17 按用户要求建立项目内可见的 `资料库/`：旧 Notion 原始归档整体迁入，Notion 与 Galaxy 内容统一保存为逐帖正文、元数据和本地媒体，保留来源、版本、下载缺口及校验记录。已实现的存储约定和后续导入入口见[个人笔记资料库工具](../../prototypes/note-library/README.md)；私人数据和批次状态由资料库内的索引及导出记录维护。此项归档工具未接入 Core，知识加工与检索能力仍按上述候选试验验收。

- 如何让短关键词找回具有相同意义、用途或相关情境的帖子，并评估遗漏与误关联？
- 图片／视频如何进入搜索范围；未提取内容造成的覆盖缺口如何表达？
- 如何支持查看更广的相关候选，并用真实样本判断是否接近用户期望的完整找回？
- 语义搜索、标签、人工 review、摘要与知识库页面应如何组合？
- AI 是否参与、使用什么分类结构，等待真实帖子样本评测后决定。
- 历史方案中的[待删除区](../history/early-roadmap.md#待删除区)尚未实现，也未明确确认采用或废弃。它的触发条件是完整对账确认点赞和收藏关系都消失，并非作者删除帖子。是否纳入、关系对账依据及本地保留/删除交互仍待产品决策。
- 写回操作是否可行、应使用哪个账号以及如何验证结果，等待独立研究。

## 当前不做的决定

- 不凭单次身份验证确定最终在线采集架构，浏览器与协议的完整链路仍需各自验收。
- 已实现的 Core v1 来源扩展以 Core 契约为准，剩余写回等身份概念不自动成为协议承诺。
- 不在真实样本评测前确定 AI 分类方案。
- 不把写回构想写成已承诺功能。
