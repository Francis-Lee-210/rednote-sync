# 项目设计想法、进度整理

## 文档定位

这份文档保存项目需求、历史思路、候选路线和仍未解决的问题，不是当前实现的技术规格。Stage 3 已经有正式离线实现；实际契约和阶段边界以 [Core README](../../projects/rednote-sync-core/README.md) 与 [Core 实现规格](../../projects/rednote-sync-core/docs/sync-core.md) 为准。

同一个问题可能同时存在两条或多条互相竞争、甚至彼此冲突的思路。这些内容可以并列保留，之后再通过调研、实验和风险评估逐步排除或合并。候选工具的当前证据和采用结论统一记录在[研究总表](../../research/catalog.md)，不再以本文件中的早期印象为准。

为了避免后续回看时混淆，可以在新增内容前使用以下状态标记：

- `[需求]`：我希望项目最终满足的真实需求。
- `[想法]`：目前想到的可能方案，还没有验证。
- `[外部声明]`：来自项目 README、官网、Issue 或其他人的描述。
- `[静态证据]`：通过阅读代码、配置或离线样本能够直接确认的行为。
- `[本地验证]`：已经在本地实际运行并观察到结果。
- `[待研究]`：已经提出具体问题，但还缺少足够证据。
- `[待决定]`：存在多个选择，需要以后结合证据作出判断。
- `[已排除]`：经过研究后明确不再考虑，并记录排除原因。

这些标记只表示信息当前所处的状态，不表示优先级。随着调查推进，同一条内容可以从“想法”或“外部声明”升级为“静态证据”或“本地验证”。“待研究”通常需要补证据，“待决定”通常需要在几个已有选项之间权衡。

## 核心目的

在我使用小红书这个社交软件的过程中，我积累了 2000 多条点赞或收藏过的帖子。这些帖子我都认为在某些方面或某种程度上有一定的价值：未必是生产力相关，也有可能是美学积累、心理状态分析、想买的商品种草帖，或者单纯是一些我觉得比较搞笑的网络梗图。

但是，小红书平台的点赞和收藏搜索系统做得非常差，经常搜不到我想找的历史帖子。主要面临以下几个痛点：

1. 即使我完全记得标题、按原标题搜索也搜不到，只能手动一条条往下翻，或者用网页搜索功能才能找到。
2. 大量帖子并没有明确的搜索关键词。帖子作者给帖子定的标签，也无法被小红书自带的搜索功能检索到。
3. 存在一些作者过一段时间后删除帖子，或者帖子失效的情况。
4. 而且由于它本身信息流软件的性质，很多时候我想再次打开，去寻找之前的帖子，但在过程中很容易被信息流中其他新出现的帖子分散注意力。久而久之，就积累了大量未处理的帖子。

这几大原因让我想把个人点赞或收藏过的小红书帖子导出到本地，导出应该包含帖子的所有信息，包括文字、图片、视频、作者信息、作者给的帖子标签等等。
此外，我希望在导出到本地的基础上，能够通过当今的 LLM 或 AI 能力对帖子进行分类和处理，最好能够搭建成为我的个人知识库。
通过对这个知识库的整理、增量更新以及有选择的删除，我可以积累更多的知识，并且在需要用的时候能够及时检索到。

## 目标

### 短期目标

先验证一套个人可用的方案：按照下文的完整度定义，把小红书点赞和收藏帖子保存到本地，支持增量更新，并以这些本地内容为基础建立个人知识库。

### 长期目标

如果个人方案经过长期使用后足够稳定，再考虑封装成软件、浏览器插件或其他形式，并研究商业化的可行性。

## 思路

我借鉴了一些当前的开源项目，以及市面上成熟或不成熟的工具、其他人的解决方案。

### 导出帖子的链接

我借鉴了别人的一款脚本，已经在 Chrome 的油猴扩展中成功安装，并取得过点赞、收藏帖子的链接列表。列表的完整度和重复获取的稳定性仍需验证。

### 导出每篇帖子的所有信息

#### 导出完整度的定义

这里所说的“完整导出”，不是保存小红书与帖子有关的所有平台数据，而是尽可能完整地保存帖子主体内容，以及后续检索、增量同步和判断数据来源所需的信息。

MVP 必须保存：

- 稳定标识：`note_id`
- 基本内容：标题、正文、帖子类型
- 作者信息：作者 ID、昵称
- 原作者标签
- 发布时间和更新时间（如果接口能够提供）
- 来源关系：点赞或收藏；如果以后支持个人发布，再增加相应来源
- 原始帖子链接
- 封面
- 全部正文图片，并保留原始顺序
- 视频文件（优先）或可用的视频地址
- 获取时间和最近成功获取时间
- 下载状态、缺失内容和失败原因

特殊媒体的处理：

- 如果帖子包含 Live Photo，应尽量同时保存静态图片和对应动态文件。
- 如果只能取得其中一部分，应保留已取得的内容，并标记为 `partial`。
- 图片、Live Photo 和视频必须保留在原帖中的顺序与对应关系。

评论可以在以后作为可选功能研究。评论数量大、变化频繁，而且会增加请求量和风控风险，因此不应阻塞帖子主体的导出。

收藏专辑属于“用户与帖子的组织关系”，而不是帖子主体。若后续支持收藏导出，可以额外保存专辑 ID 和专辑名称，但同一帖子仍只保存一份主体内容。

#### 增量更新规则

导出后的帖子应保存在本地。实现增量导出，不重复导出已有帖子。

MVP 只处理点赞和收藏。个人发布可以作为未来能力保留，但不进入当前增量同步流程。

以下是为了避免数据误删、重复下载和历史版本丢失而记录的规则设想。它们描述希望系统表现出的行为，具体的数据表、字段名、检查频率和重试参数都还没有定稿。

##### 唯一标识与来源关系

- 使用 `note_id` 作为一篇帖子主体内容的唯一标识。
- 同一帖子同时出现在点赞和收藏中时，只保存一份主体内容。
- 点赞和收藏应记录为独立的来源关系，例如 `liked` 和 `collected`，不能因为其中一种关系消失就删除帖子主体。
- 每种来源关系应分别记录首次发现、最近一次确认存在，以及确认移除的时间。

##### 首次同步、增量同步与来源对账

- 首次运行需要分别完整扫描点赞列表和收藏列表，建立本地基线。
- 后续日常同步优先获取新增加的点赞和收藏；已经存在且内容没有变化的帖子不重复下载。
- 仅扫描最新内容无法可靠判断旧帖是否已经被取消点赞或取消收藏，因此需要另行进行低频、分批的完整来源对账。
- 一轮来源对账需要记录本轮实际看见的全部 `note_id`。只有整轮扫描完整并成功结束后，才能将本轮没有出现的来源关系标记为已移除。
- 如果对账中途停止、请求失败或没有扫描到底，不得据此判断用户取消了点赞或收藏，也不得移除任何已有来源关系。

##### 作者修改与版本快照

- 已保存的帖子需要通过低频、分批、轮转的方式重新检查，不在每次同步时重新请求全部 2000 多条帖子。
- 每次成功获取帖子后，对规范化的主体内容计算内容指纹。主体内容包括标题、正文、原作者标签、媒体内容及媒体顺序。
- 如果内容指纹没有变化，只更新 `last_checked_at` 和最近成功获取时间，不创建新版本。
- 如果作者修改了标题、正文、原作者标签、图片、视频、Live Photo 或媒体顺序，应保留修改前的版本快照，并将新版本设置为当前内容。
- 版本记录需要保存变更时间和发生变化的字段。没有变化的媒体可以按照内容哈希复用，不重复保存相同文件。
- 点赞数、收藏数、评论数和分享数等互动数据只更新当前元数据，不触发主体内容版本快照。

##### 远端状态与本地状态

状态需要按不同含义分开记录，避免把“下载失败”“作者删除”和“用户不再收藏”混为一谈。下面的名称只是当前示例：

```text
source_relations  # liked / collected 是否仍然存在
remote_status     # available / unavailable_suspected / deleted
local_status      # active / pending_deletion / archived
sync_status       # pending / done / partial / failed
```

- 只有远端明确返回帖子不存在时，才能把 `remote_status` 标记为 `deleted`。
- 普通网络失败、token 失效、登录失效、权限问题或可能的风控错误，只能记录具体失败原因并标记为 `unavailable_suspected`，不能直接推断作者删除了帖子。
- 无论远端帖子已删除还是暂时无法访问，本地最后一次成功导出的版本都应继续保留。

##### 待删除区

- 只有一轮完整且成功的来源对账确认 `liked` 和 `collected` 都已经消失后，帖子才进入待删除区。
- 待删除区采用逻辑标记，即设置 `local_status: pending_deletion`。正文、历史版本和媒体仍保留在原位置，避免移动文件导致引用失效。
- 待删除内容永不自动永久删除，必须由用户选择保留为归档、恢复为正常内容，或永久删除本地正文、版本和媒体。
- 如果待删除或已经由用户永久删除的帖子以后重新出现在点赞或收藏中，应把它视为新的用户意图，自动恢复或重新导入，并清除对应的待删除状态或删除墓碑。

##### 失败重试与同步暂停

- 瞬时网络错误和可恢复的服务端错误可以使用带随机抖动的指数退避进行重试。自动重试的次数和间隔需要通过实验决定，不能直接把某个工具的默认值当成结论。
- 登录失效、验证码、风控或权限错误不应连续自动重试。出现这类错误时应暂停相关同步并等待人工处理。
- 单篇帖子最终失败后，应先持久化失败阶段、错误原因、尝试次数和下一步动作，再允许同步游标继续推进，避免一篇失败帖子永久阻塞整个批次。
- 已经取得部分正文或媒体的帖子应保留已有结果，并标记为 `partial`，后续可以只重试缺失部分。

##### 需要覆盖的场景

- 同一帖子先点赞、后收藏：只保存一份主体，同时记录两个来源关系。
- 重复同步且主体内容未变化：不创建新版本，也不重复下载媒体。
- 作者修改正文或媒体：保留旧版本快照，并生成新的当前版本。
- 只有互动数据变化：更新元数据，但不创建主体版本。
- 作者删除帖子：保留本地最后成功版本并更新远端状态。
- 来源对账中途失败：不移除任何点赞或收藏关系。
- 完整对账确认只取消点赞：移除 `liked`，继续保留 `collected`。
- 完整对账确认两种关系都消失：进入逻辑待删除区，等待用户决定。
- 待删除帖子重新被点赞或收藏：自动恢复为正常内容。
- 瞬时下载错误达到配置的重试上限：进入失败处理队列。
- 登录、验证码或风控错误：暂停同步，不继续自动尝试。

#### 采集方式与账号风险的两条探索路线

由于小红书有非常恶心的反爬机制，它会标记可疑用户，并限制可疑用户的曝光量，甚至可能导致直接封号。目前可以同时保留两条不同的探索路线：

1. 路线 A：使用用户自己的账号。这种路线必须非常保守，尽量贴近用户正常浏览行为，降低请求频率，支持随时暂停，并在出现登录异常、验证码或疑似风控时停止继续操作。因为涉及用户长期使用的真实账号，这条路线应优先控制账号风险，而不是追求导出速度。
2. 路线 B：寻找不直接依赖用户主要账号的其他办法。可以继续研究小红书小号、代理、Cookie 或账号隔离、浏览器环境、签名机制、逆向开发以及其他尚未想到的方案。这些目前都只是候选研究方向，需要分别判断是否可行、是否仍然存在账号或数据风险、能否长期维护，以及是否适合个人方案或未来产品化。

当前不在这两条路线之间做最终选择，也不假定它们一定互斥。可能的结果包括：只采用第一条路线、找到足够可靠的替代路线、针对不同操作组合使用多种路线，或者经过研究后放弃其中一部分思路。

可以参考其他现成的下载工具，但目前还不知道它们是否仍然依赖账号 Cookie，也不能只凭 README 中的“反风控”描述判断账号是否安全。

#### 候选工具与方案的调查方法

候选工具最初根据 Star 数量、README、官网或个别 Issue 收集。现在主要候选已经完成固定 revision 源码审查，但下面的调查方法仍作为以后新增对象的统一标准。Star 数量只能说明关注度，不能证明功能真实可用、当前版本仍然有效，也不能证明它适合本项目的账号风险、数据完整度和维护需求。

调查候选工具时，尽量为每个项目记录以下信息：

- 基本身份：项目地址、当前版本、最近更新时间、维护活跃度和许可证。
- 目标用户：个人归档、内容创作者、运营工具、研究爬虫，还是通用 API。
- 数据范围：是否支持个人发布、点赞、收藏、收藏专辑、单篇链接和评论。
- 内容完整度：是否能获取正文、原作者标签、全部图片、视频、Live Photo、作者和时间信息。
- 增量能力：是否有稳定 ID、去重、游标、失败恢复、来源关系和作者修改检查。
- 登录与请求方式：是否依赖用户浏览器会话、Cookie、页面环境、签名算法、远端服务或第三方账号。
- 风险控制：请求频率、退避和暂停机制、验证码处理，以及已知的风控或封号报告。
- 输出与集成：保存格式、媒体目录、数据库结构，以及能否接入本地知识库。
- 可维护性：是否容易因网站更新失效，是否依赖作者服务器，代码是否足够清晰，能否替换其中的单个组件。
- 商业化限制：开源许可证、第三方服务条款，以及是否允许修改、分发或用于商业产品。
- 证据等级：当前结论只是外部声明、静态代码证据、本地小样本验证，还是较长时间的真实使用结果。

同一个工具可以只解决流水线中的一个环节，不要求一个项目同时完成链接发现、详情下载、媒体保存、增量同步、知识库生成和 AI 分类。调查时应先判断它适合承担什么职责，再判断是否值得复用整个项目。

在涉及真实账号之前，应优先采用 README 和文档核对、许可证检查、静态代码分析、离线样本分析，以及不触发真实平台操作的本地测试。真实账号测试的范围和停止条件需要另外设计。

#### 候选研究当前结论

- `[静态证据]` 12 个仓库对象和 1 个 Playwright 综合专题已经完成并通过独立复审，详见[研究总表](../../research/catalog.md)。
- 没有任何候选可以直接成为完整实现。现有价值主要是行为、数据契约、错误边界和交互设计参考。
- XHS-Downloader、OpenCLI、xhs-cli-export 与 Playwright 保留较高参考价值，但不等于建议直接嵌入源码或相信其账号安全声明。
- MediaCrawler、xiaohongshu-cli、xiaohongshu-mcp、ReaJason/xhs、Spider_XHS、XHS_ALL_IN_ONE、Playwright MCP 和 xiaohongshu-importer 只保留局部参考；具体排除项和许可证边界以各专项报告为准。
- Postman collection、两篇阿里云文章、JustOneAPI 与 xhs_web_crawler 等早期线索没有进入当前专项队列。只有以后出现具体证据问题时再决定是否调查。

## 当前阶段与下一步讨论

Stage 3 离线核心与候选项目静态研究已经完成。下一步不必立即实现，先讨论希望优先验证哪一种价值：

1. 离线输入桥接：把 userscript JSON 或 XHS-Downloader SQLite/媒体转换成现有 `offline-input-v1`，先闭合不接触真实账号的本地链路。
2. Stage 4 在线适配器：使用专用浏览器环境，小范围验证当前列表、详情、媒体、会话与停止条件。这条路线风险最高，需要单独授权。
3. AI 分类原型：使用合成或已经脱敏的本地内容包，验证分类 Schema、模型路由和人工复核，不等待在线同步完成。
4. 使用体验：先定义用户如何启动、查看进度、处理失败和浏览知识库，再决定 CLI、Obsidian、浏览器插件或桌面应用的优先级。

讨论时至少需要回答：哪一个结果最能证明项目对用户有用、可以接受多少手动步骤、是否愿意进行真实账号小样本验证，以及下一阶段的完成标准是什么。

## 待研究问题

这里先记录问题，不要求立即回答。研究结果应尽量附上证据来源、验证条件和结论的适用范围；暂时无法确认的内容可以继续保留为问题。

### 当前阶段优先回答

这些问题会直接影响“能否可靠地把点赞和收藏保存到本地”，优先级高于知识库界面、AI 分类和商业化形式。

#### 数据入口与账号依赖

- `[待研究]` 点赞列表和收藏列表分别可以通过哪些入口完整获取？网页、接口、浏览器自动化和现有工具各自能够覆盖到什么范围？
- `[待研究]` 首次扫描 2000 多条内容时，分页、游标、列表上限、重复项和中途恢复分别如何处理？
- `[待研究]` 获取列表与获取单篇详情是否必须使用同一个账号、Cookie、浏览器环境或设备身份？
- `[待研究]` 不使用用户主要账号的候选路线，分别能够解决哪一步，又会引入哪些新的账号、隐私、成本或维护风险？
- `[待研究]` 小红书帖子 URL 的组成和有效期是什么？目前观察到 URL 似乎包含 `note_id`、`xsec_token`、设备类型等信息，但各字段的用途、必要性和稳定性尚未确认。

#### 数据完整度与可恢复性

- `[待研究]` 各类帖子实际能取得哪些字段？图文、视频、Live Photo、长文等类型是否需要不同处理方式？
- `[待研究]` 原图、无水印媒体、视频和 Live Photo 的可用地址是否有有效期？是否必须在发现帖子时立即下载？
- `[待研究]` 帖子详情、媒体或作者信息只取得一部分时，最小可接受结果是什么？后续如何只补齐缺失部分？
- `[待研究]` 哪些远端返回能够可靠证明帖子已经删除，哪些只能说明登录、权限、token、网络或风控异常？
- `[待研究]` 本地内容指纹应如何规范化，才能既识别正文和媒体的真实修改，又避免因无关字段或地址变化产生伪版本？

#### 风险验证与停止条件

- `[待研究]` 使用用户主要账号时，哪些行为需要被视为风险信号？例如验证码、登录状态变化、请求异常、访问频率限制或账号功能异常。
- `[待研究]` 在真实账号测试前，可以用哪些离线样本、小号、静态分析或最小请求实验排除明显不可行的方案？
- `[待研究]` 每类实验的请求范围、持续时间、人工观察项和立即停止条件是什么？
- `[待研究]` 如何区分工具宣称的“反风控能力”、代码中实际存在的控制措施和真实环境下长期有效的结果？

### 后续架构问题

Stage 3 已经回答了一部分离线架构问题。下面保留尚未确定的产品体验、在线输入、备份和 AI 决策，并注明已经落地的基线。

#### 本地保存与数据模型

- `[本地验证]` Stage 3 使用 SQLite 保存 account、progress、manifest、task、failure 和 run 等 canonical 状态；不可变内容寻址对象库存媒体，Markdown/JSON/CSV/media 等派生视图可以重建。
- `[本地验证]` 原始 account/note ID 不进入路径，公开目录使用稳定 digest；对象以 SHA-256 去重，派生媒体使用普通隔离副本。
- `[待研究]` 自动清理未引用对象和用户永久删除的完整语义尚未实现；当前不自动进行 orphan object GC。
- `[待决定]` 是否保存原始响应或原始页面作为可追溯证据？如果保存，保留多久、如何处理其中可能存在的账号信息？
- `[本地验证]` Core 已有 object/receipt/derived view 校验及 `verify`、`repair-views`；`[待研究]` 用户级外部备份、迁移和灾难恢复流程仍未设计。

#### 知识库与检索体验

- `[待决定]` 知识库最终采用 RAG、LLM Wiki、Obsidian、独立应用、普通文件搜索，还是几种能力的组合？
- `[待研究]` 用户实际找回一篇历史帖子的方式有哪些：精确标题、模糊语义、图片内容、作者、时间、个人分类、使用情境或自然语言提问？
- `[待决定]` 哪些信息由原帖直接提供，哪些由用户手工补充，哪些可以由 AI 推断？这些来源在界面和数据中是否需要区分？
- `[待研究]` 图片 OCR、图片理解、视频转写和多模态检索对找回效果的实际提升有多大，成本是否值得？
- `[待决定]` 原帖被修改或删除后，检索默认展示当前版本、最后成功版本，还是允许用户查看版本时间线？

#### AI 整理与分类

- `[需求]` AI 结果必须与原始归档分离，记录模型、提示词、分类体系和内容包版本，并允许人工纠正。
- `[想法]` 当前分类设计采用主题、用途、形式、情绪、美学和实体等多维分类卡，不把帖子强制放进唯一文件夹；实际标签体系仍需真实样本验证。
- `[待决定]` AI 的首个产品职责是摘要和标签、辅助搜索、发现关联，还是进一步整理成专题知识？
- `[待决定]` 用户手工修改过的分类和描述是否永远优先于 AI 结果？模型更新后是否允许重新处理旧内容？
- `[待研究]` 哪些处理可以完全在本地完成，哪些可能需要远端模型？上传正文、图片或视频时有哪些隐私和成本问题？
- `[待研究]` 如何建立一个小型人工标注样本，用来比较不同模型、提示词和分类结构，而不是只凭少量直觉案例选择方案？
